# NIPs

NIP 是 **Nostr Implementation Possibilities** 的缩写。

它们用于记录兼容 [Nostr](https://github.com/nostr-protocol/nostr) 的 _relay_ 和 _client_ 软件可以实现的内容。

这里列出的 NIP 不是一份协议清单。没有任何东西强制任何软件实现某个 NIP。每个应用都会选择与自身用例相关的子集。不要仅仅因为某个东西存在于这个仓库中就去实现它。其他标准和 NIP 也可能存在于本仓库之外，例如以 pull request 的形式存在，并且可能已经在实际环境中部署；实现时也应该考虑它们。

## 消息类型

### Client 到 Relay

| type    | description                          | NIP         |
| ------- | ------------------------------------ | ----------- |
| `EVENT` | 用于发布事件                         | [01](01.md) |
| `REQ`   | 用于请求事件并订阅新的更新           | [01](01.md) |
| `CLOSE` | 用于停止之前的订阅                   | [01](01.md) |
| `AUTH`  | 用于发送认证事件                     | [42](42.md) |
| `COUNT` | 用于请求事件计数                     | [45](45.md) |

### Relay 到 Client

| type     | description                                | NIP         |
| -------- | ------------------------------------------ | ----------- |
| `EOSE`   | 用于通知 client 所有已存储事件都已发送     | [01](01.md) |
| `EVENT`  | 用于向 client 发送其请求的事件             | [01](01.md) |
| `NOTICE` | 用于向 client 发送人类可读消息             | [01](01.md) |
| `OK`     | 用于通知 client 某个 EVENT 是否成功        | [01](01.md) |
| `CLOSED` | 用于通知 client 某个 REQ 已结束及其原因    | [01](01.md) |
| `AUTH`   | 用于发送认证挑战                           | [42](42.md) |
| `COUNT`  | 用于向 client 发送请求的事件计数           | [45](45.md) |

## 本仓库接收 NIP 的标准

1. 在适用时，它们应至少被两个 client 和一个 relay 完整实现。
2. 它们应该是合理的。
3. 它们应该是可选且向后兼容的：必须谨慎设计，使选择不实现它们的 client 和 relay 在与选择实现它们的软件交互时不会停止工作。
4. 同一件事不应该有超过一种做法。
5. 其他规则会在必要时制定。

## 这个仓库是中心化因素吗？

为了促进互操作性，我们需要所有人都能遵循的标准，也需要这些标准定义出**每件事的唯一做法**，同时绝不损害**向后兼容性**。为此，无法绕开让大家就同一件事达成一致，并维护一个中心化的标准索引。不过，这样一个索引的存在并不会损害 Nostr 的去中心化。_只要中心索引无法满足协议需求，它随时都可以受到挑战_，并且可以迁移到其他地方，由其他人维护。

它甚至可以 fork 成多个版本，然后一些 client 走一条路，另一些 client 走另一条路，还有一些 client 同时遵循相互竞争的标准。这会稍微损害 Nostr 的简洁性、开放性和互操作性，但短期内一切仍然可以工作。

有一份知名 Nostr 软件开发者列表，他们拥有本仓库的提交权限，但这主要出于实践上的原因。由于我们处理的事物本身具有这种性质，仓库所有者可以按自己的意愿撤销成员资格并重写历史；如果这些行为没有正当理由，或被认为是糟糕甚至恶意的，社区就必须作出反应。

## 这个仓库如何运作

标准可以通过两种方式出现：第一种是有人开始做某件事，然后其他人复制它；第二种是有人提出一个新标准的想法，这个想法能够让多个 client 和整个协议受益，同时不破坏**向后兼容性**以及**每件事只有一种做法**的原则。然后他们把这个想法写下来并提交到本仓库，其他感兴趣的人阅读并给出反馈。等大多数人形成合理共识后，我们将其编纂为一个 NIP，感兴趣的 client 和 relay 开发者就可以继续实现该功能。

本仓库支持这两种标准化方式。虽然更倾向于第二种方式，但我们也会努力把本仓库之外出现的标准编纂成 NIP，使其之后可以被引用，也更容易被其他人理解和实现。不过显然，和任何由人组成的系统一样，当某些标准被认为有害时，也可能需要酌情处理。
